# Shared diagram geometry contract

**Status:** Contract for the planned shared geometry work; implementation remains unchanged. **Baseline:** `e8130af860f8c7933a498aa8811ca96998eecdf5`.

## Geometry and obstacles

- Use finite page-space coordinates for planned geometry; serialize vertex geometry relative to its declared parent. Convert child bounds to page space before collision checks. IDs `0` and `1` remain reserved for the draw.io root and default layer.
- Treat each visible node, container boundary, and independently rendered text label as an obstacle with a conservative measured bounding box. Measure labels after wrapping and include font size, padding, and line height; text-width estimates are layout estimates, not font metrics. Keep unrelated nodes, labels, and route segments clear by a documented clearance. Containment is not an obstacle collision.
- Every route is orthogonal: each segment is horizontal or vertical and each bend is 90 degrees. A route must not pass through an unrelated node or label. Edge-to-own-endpoint contact is allowed. **No route segment may overlap or share a trunk with another edge.** Parallel and reverse edges receive distinct ports and tracks. Route crossings are separate from shared trunks and are permitted only where the diagram-specific rules below allow them.
- Allocate lanes globally per diagram, not one edge at a time: reserve node/label bounds, endpoint approach space, ports, and distinct route tracks before assigning bends. Assign stable ordering by semantic IDs so equivalent input produces repeatable geometry. Expand inferred page bounds to include all planned vertices, labels, and route points; preserve explicit page dimensions and diagnose overflow.
- Declare ports explicitly on each edge end (node ID plus side and normalized offset, or an equivalent named port). Distribute multiple ports deterministically along a side with clearance. Do not rely on draw.io automatic perimeter selection to choose a route. A semantic edge has its real semantic nodes as endpoints; invisible helper vertices are permitted only as documented renderer internals and must not replace semantic endpoints in the returned model.
- Allocate an edge label as an obstacle with its own bounds and association to one edge. Place it beside a selected route segment, with readable padding, without covering a node, another label, or an unrelated route. Labels may mask their own edge only when the renderer explicitly uses an opaque label background; this exception does not authorize a shared route.

## Planned geometry and exported geometry diagnostics

Diagnostics have stable `severity`, `code`, `path`/subject, human-readable message, and relevant measured value; findings must identify whether they concern **planned** semantic layout or **exported** draw.io XML. Errors reject invalid input/model structure; warnings report quality or limits without asserting domain truth.

- **Planned geometry:** renderers diagnose non-finite/negative dimensions, duplicate or unresolved semantic IDs, missing ports, non-orthogonal bends, node/label obstruction, shared or coincident edge segments, invalid lane assignments, and explicit-page overflow before serialization. A planned-layout error prevents XML output. A remaining route crossing is a warning unless its diagram-specific rule prohibits it.
- **Exported geometry:** the validator checks XML parseability; cell ID, parent, and endpoint resolution; finite vertex/point geometry; page/parent bounds; explicit waypoint orthogonality; and measurable node, label, route, port, or shared-segment collisions. Structural invalidity is an error. Bounds and likely visual collisions are warnings. Auto-routed edges without explicit waypoints cannot receive a route-quality pass: report them as unchecked, not clear. PNG review may reveal rendered-font or renderer-specific differences and supplements XML checks.
- Do not silently treat invisible helper cells, labels, edges, containers, or style-text matches as ordinary visible obstacles. Classify by renderer metadata where available; in imported XML, use conservative documented recognition and report uncertainty instead of skipping a whole class of checks.
- Diagnostics do not validate business semantics or notation truth. Visual review of exported images remains necessary for legibility and renderer-specific shape appearance.

## Renderer coordination interface

`scripts/geometry.mjs` exports `routeOrthogonalEdges({ obstacles, edges, page, clearance })`. Each obstacle is `{ id, kind: 'node'|'label'|'container'|'helper', bounds: { x, y, width, height }, ownerId? }` in page coordinates. Each edge request is `{ id, source: { nodeId, port?: { side, preferredOffset? } }, target: { nodeId, port?: { side, preferredOffset? } }, label?: { id, width, height } }`. `side` is exactly `north|east|south|west`; a supplied `preferredOffset` is normalized to `[0,1]` along that side, with `0.5` as the default preference. The router assigns unique ports even when preferences collide. Its deterministic result is `{ routes, diagnostics, page }`; each route is `{ edgeId, sourcePort: { nodeId, side, offset, point }, targetPort: { nodeId, side, offset, point }, points: [{ x, y }], bounds, label?: { id, bounds, segmentIndex, position } }`. `points` are ordered orthogonal bend points between the resolved port points. `bounds` includes endpoints and bends. A route result contains no positive-length segment shared with another route; impossible placement returns a phase-tagged error diagnostic rather than a silently overlapping route.

The shared cell model is `{ kind: 'vertex', id, value, style, parent, geometry: { x, y, width, height } }` or `{ kind: 'edge', id, value, style, parent, source, target, ports: { source: { side, offset }, target: { side, offset } }, geometry: { relative: 1, sourcePoint?, targetPoint?, points: [{ x, y }] } }`. Model vertex geometry is parent-local; route and label planning is page-space and converts points to the edge parent's coordinates during serialization. `scripts/common.mjs` exports `serializeCells(cells)` to encode typed models as existing editable `mxCell`/`mxGeometry` XML, including explicit port constraints and waypoints. Existing `vertex()`/`edge()` string helpers and semantic renderers remain supported unchanged during migration; `serializeCells` passes through legacy XML cell strings.

Diagnostics use `{ phase: 'planned'|'xml', severity: 'error'|'warning'|'unchecked', code, path, message, value? }`. `unchecked` means the corresponding property is not measurable from this input; it must never be counted as a successful check. Router failures use `phase: 'planned'`; `inspect()` reports measured serialized facts using `phase: 'xml'`, keeps its existing `errors` and `warnings` collections, and adds `unchecked` for auto-routed edge geometry whose actual path is absent. Planned diagnostics are never copied as proof about serialized or rendered geometry. The XML validator independently checks parsed models, not router claims.

`scripts/render_drawio.mjs` exports `registerRenderer(type, renderer)` and `renderInput(data, { style, renderers })`. A renderer takes normalized semantic input, resolved styles, and shared geometry helpers, and returns `{ cells, diagnostics, page }`; it does not serialize XML or write files. Built-in type dispatch uses the registry. The `class` type has a registration slot only and raises a structured unsupported-type error until another workstream registers it. The CLI owns input/output and calls `serializeCells` after dispatch.

Preserve existing CLI entry points and valid JSON aliases during migration: sequence string participants and missing `kind` defaulting to sync; ERD `attrs`, `a`/`b`, and short attribute keys `n/t/k`; DFD `processes`/`edges`, name/label endpoints and flow `text`; generic `attrs` and top-level aliases; current use-case and activity input forms. Canonical values win only under an explicit compatibility rule; conflicting aliases produce a diagnostic, never a silent geometry choice. Keep semantic IDs stable across layout changes. Presentation styles cannot alter semantic direction, cardinality, or UML arrow meaning.

## Legal diagram-specific intersections

- **Sequence:** lifelines intentionally pass through message bands and fragment frames; a message connects to its own participant lifeline endpoints. Fragment frames contain their branch content; separators remain within their frame. Self-messages loop out and return to the same lifeline on a distinct orthogonal track. Unrelated message routes and labels still obey the no-shared-trunk and obstacle rules.
- **ERD:** an edge may terminate on its declared entity or attribute row, and its own cardinality markers occupy the endpoint. Attribute rows are contained in their entity. Distinct relationships, including relationships with a common endpoint, use different ports/tracks and never share a segment. Relationship labels may not cover entities or unrelated relations.
- **DFD:** a flow may touch only its declared source and target nodes; distinct parallel/reverse flows use separate ports and tracks. Store glyph/label helper parts are a documented composite for one store, not independent nodes. No other node, label, or flow may be crossed or overlapped.
- **Use case:** a system boundary contains use cases and its title; actor symbols have separate actor labels. Association and use-case relation edges connect their declared endpoints. Routes may cross only when the renderer marks that relation type as crossing-permitted and the crossing is visually unambiguous; they may never share a trunk. Otherwise route around nodes and labels.
- **Activity:** initial, action, decision/merge, and final nodes are distinct; final-node inner marks are intentional containment. Transitions touch only declared endpoints. Guard labels remain clear of nodes and unrelated transitions; no transition shares a route segment.
- **Generic cells:** only explicit parent containment and declared edge endpoints are intentional. All other geometry follows the common obstacle and route rules.

## Source-backed problem causes

At this baseline, each semantic renderer largely calculates placement and cells locally. `scripts/activity.mjs` falls back to a fixed three-column position formula; `scripts/erd.mjs` lays entities on a square-root grid and routes relations independently; `scripts/sequence.mjs` spaces participants from text estimates and schedules message/fragment labels within bands; `scripts/dfd.mjs` uses three kind-based columns and per-pair route slots; `scripts/usecase.mjs` uses a constrained fixed boundary/grid arrangement. These algorithms do not share one obstacle map or global lane allocator, so independently plausible routes can converge, cross, or compete for the same corridor. ERD evidence: final `erd.png` shows long aligned relationship trunks and visually tight crossings; the individual `.drawio` relation cells use `orthogonalEdgeStyle` with only endpoint perimeter anchors and no explicit route-point arrays for those inter-entity links.

The current `scripts/validate_drawio.mjs` checks XML structure, vertex bounds, finite route points, and a sibling-vertex overlap heuristic. It does not compute route segment intersections, label bounds, or automatic edge geometry; it skips endpoint cells and any vertex whose style contains `umlLifeline` or `umlFrame`. Thus `evaluation.md` can truthfully report zero detected overlaps while PNG inspection exposes routing quality issues. The FitTrackAI sequence PNG also shows the self-call as a small loop at its source lifeline; `scripts/sequence.mjs` represents messages with separate 2×2 invisible endpoint vertices and a local loop waypoint, but does not expose that route to a shared obstacle/clearance check. `evaluation.md` records that the early ERD needed entity reordering and attribute-row endpoints to avoid header crossings, corroborating the placement/endpoint sensitivity. These are geometry and validation coverage gaps, not evidence of incorrect domain content.
