# Notation, overrides, and visual templates

The semantic renderers implement useful subsets of diagram conventions. They do not claim complete formal UML conformance, validate every UML well-formedness rule, or determine whether the modeled system is correct. Confirm uncertain domain meaning with the project owner.

## Notation decisions

These are semantic choices, kept separate from connector/native-shape overrides and appearance templates below.

- **Use case:** model actors, use cases, system boundaries, associations, `include`, `extend`, and generalization. This follows the core elements and relationship vocabulary in the [Visual Paradigm use-case notation guide](https://circle.visual-paradigm.com/docs/uml-and-sysml/use-case-diagram/use-case-diagram-notations-guide). The renderer verifies declared endpoints; it does not validate all UML constraints on include/extend direction or use-case meaning.
- **Sequence:** participant columns represent interaction participants and vertical position orders messages over time, consistent with [Visual Paradigm's sequence overview](https://www.visual-paradigm.com/guide/uml-unified-modeling-language/what-is-sequence-diagram/) and [IBM's sequence-diagram guide](https://developer.ibm.com/articles/the-sequence-diagram/). Implemented message kinds are `sync`, `async`, and `return`; the static combined-fragment subset is `alt`, `opt`, `loop`, and `par`, with guarded operands. `par` is a static depiction, not a scheduler. Self-messages use a distinct orthogonal loop route.
- **Class:** classes render a name header plus attribute and operation compartments. The subset supports visibility markers, attribute types, operation parameters and return types, and association, dependency, generalization, aggregation, composition, and realization relationships. This follows the class compartments and relationship concepts described in [Visual Paradigm's class-diagram overview](https://www.visual-paradigm.com/guide/uml-unified-modeling-language/what-is-class-diagram/) and [introduction to class diagrams](https://www.visual-paradigm.com/guide/introduction-to-class-diagrams/). It does not infer missing model facts or guarantee all UML relationship constraints.
- **Activity:** actions and control nodes are connected by directed transitions; implemented node kinds are `initial`, `action`, `decision`, `merge`, `final`, `activityFinal`, and `flowFinal`. Transition guards/labels are display text, not executable conditions. This is a subset of the control-flow notation described by [Visual Paradigm's activity-diagram guide](https://circle.visual-paradigm.com/docs/uml-and-sysml/activity-diagram/how-to-draw-a-activity-diagram-in-uml/). Object flows, swimlanes, fork/join nodes, and broader UML activity semantics are not implemented by this renderer.
- **ERD:** entities contain named attribute rows and optional key markers; relations can attach to entities or named attributes and accept explicit end values `1`, `0..1`, `0..*`, and `1..*`. The renderer uses the Crow's Foot endpoint family described in [Lucid's ERD symbol and notation guide](https://lucid.co/diagram/erd/symbols-and-notation). Cardinality is caller-supplied, never inferred from names. This is a renderer convention, not a universal ERD standard.
- **DFD:** this renderer chooses a process-mediated convention with process, external-entity, and data-store nodes plus directed, optionally labeled data flows. Each flow must touch a process; this is the selected Yourdon/DeMarco-style rule, not a universal restriction on all DFD dialects. The concepts of sources, processes, stores, and data paths are described in [IBM's DFD overview](https://www.ibm.com/think/topics/data-flow-diagram). The data-store drawing is a visual composite approximating the concept, not a claim of exact conformance to every notation family.

## User-specific connector and native-shape overrides

Only record an override here when the user explicitly requests a connector or native shape, or supplies an approved diagram-specific mapping. Keep semantic direction, cardinality, relationship type, and data-flow meaning intact when applying presentation overrides. An override does not make a shape or connector semantically equivalent under UML or a DFD/ERD notation.

Style sources are resolved as renderer fallback, `scripts/style.json`, input `style`, then `--style overrides.json`; a generic cell's inline style is supplied directly. `--style` only accepts known configuration keys. Do not treat a renderer default as a user preference. When a requested native style key is not evidenced by an installed shape definition or checked-in exported example, ask for a reference or use a documented supported alternative rather than guessing.

## Visual templates

The repository's layout and formatting defaults are templates, not notation rules or user-specific facts. Examples include sequence participant headers, dashed lifelines and fragment frames; ERD row-based entities, key markers and routed relations; the DFD's distinct node appearances and flow labels; and the use-case boundary/grid arrangement. Activity and class dimensions respond to estimated label/member content. Font measurement is an estimate; diagrams.net Desktop determines actual rendered appearance. Review an export for clipping and legibility.

## Geometry, diagnostics, and limits

Semantic component renderers use the shared planned orthogonal router for nodes, explicit ports, and distinct routes; route planning can fail when page bounds or obstacle constraints leave no route. Generic `elements[]` input remains caller-laid-out. See [the geometry contract](docs/geometry-contract.md) for the route result and serialized checks.

Planned-layout diagnostics describe the renderer's geometry model. The XML validator separately measures explicit serialized waypoints and visible cell bounds where supported. Automatic editor routes do not expose a stored path and must be marked unchecked. Neither diagnostics phase proves final font layout, notation correctness, or domain semantics. Review diagrams.net exports.
